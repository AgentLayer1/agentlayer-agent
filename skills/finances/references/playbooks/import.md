# Import

**You own that every statement lands once, proven against its own balances, and filed where the books will find it.** A bank, card, wallet or payment-platform statement or export handed over ("import ~/Downloads/october.csv"), files waiting in `data/inbox/`, or a sync nudge that the inbox has files.

1. **Bring it in, then list what's waiting.** A file the operator names elsewhere ("~/Downloads/october.pdf") goes in with the `capture` tool, `kind: "finance"` and its `file` path: it copies the file into `data/inbox/` byte for byte, leaves the download where it was, and reports a duplicate when the same file is already waiting or imported. Then take every file in `data/inbox/` (not `.staged/`).
2. **Tell a receipt from a statement.** A receipt or invoice (one purchase: a merchant, a date, a total, often its items) isn't imported as a statement. Read it (never transcribing a residential address), then file it with `bun "${CLAUDE_SKILL_DIR}/scripts/receipts.ts" add <file> --date YYYY-MM-DD --merchant <name> --amount N --currency CUR --items "<what was bought>" --entity <slug>` and run `receipts.ts match`. It links the receipt to the one statement line it fits (same currency and amount, dated a day before to five days after, the merchant in the line's text); when none or several fit, show the candidates and ask, then `receipts.ts link <receipt> <line>`. A receipt for a company, or for a personal tax relief (medical, books, a gym), also goes through the tax playbook's [capture](tax/capture.md), so the books record it once. A matched receipt's items are evidence when categorising (step 5 of [dashboard](dashboard.md)). Then continue with the next file.
3. **Name the account.** Match each file to an account under an entity profile's `## Accounts` (the institution and the last digits on the statement usually decide it). Ask when it isn't clear whose account it is: a company's statement filed under the operator, or the reverse, puts money in the wrong books. An export per currency (a multi-currency wallet) is one account per currency (`acme-usd`, `acme-myr`), sharing the institution's column map; a currency with no lines in the period is skipped. A new account is added to its profile first as `- { id, name, institution, type, currency }` (`type` is `current`, `savings`, `card`, `wallet` or `platform`); ids are unique across entities, and a name carries at most the last four digits, never a full account number. An import refused with "has no currency yet" means the entity's profile doesn't pin one: ask the operator which currency it pays tax or is registered in, add `currency:` to its frontmatter, and import again.
4. **Get the lines in the engine's shape**, by format:
   - **CSV or XLSX:** the account's institution needs a column map at `importers/<institution>.md` (or the account's `importer:`). When there isn't one, learn it once: look at the first rows of the export (the header, the date style, whether money out is a minus, a debit column, or a positive number on a card), then write the file with flat frontmatter (`institution`, `format`) and a yaml block under `## Columns`:
     ```yaml
     date: Posting Date
     date_format: DD/MM/YYYY      # tokens: YYYY YY MMM MM M DD D
     description: [Description, Reference]
     debit: Withdrawal            # or amount: Amount
     credit: Deposit
     balance: Balance             # leave out when the export has none
     invert: false                # true when charges are positive (most card exports)
     ```
     When the export has a merchant or payee column, list it first in `description` (`[Merchant, Description]`): the description alone often starts with boilerplate ("Card transaction of 20.76 USD issued by …"), which would make every line a different payee. A column map holds column names only, never figures. Every later export from that institution imports without the model.
   - **PDF with a column header** (date, money out, money in, balance across the top of the transactions): run `bun "${CLAUDE_SKILL_DIR}/scripts/pdf.ts" <pdf> --importer <institution>`. It reads the statement through the layout in `importers/<institution>.md` (`format: pdf`, yaml under `## Layout`) and writes the staged CSV, printing the opening and closing it found, the lines it `skipped` (no money in or out) and the lines `charged` a fee or tax. When the institution has no layout yet, run it with `--draft` instead (the PDF first, then the flag): it prints the header rows it found and a layout to start from. Check the draft against the statement, then save it from [importer-template](../importer-template.md) as `importers/<institution>.md`; every later statement from that institution reads without the model. It needs `pdftotext` (poppler); when it's missing, relay the install hint it prints and stop.
   - **Any other PDF** (no column header, one amount column with its direction in words, or no `pdftotext`): read its text with `pdftotext -layout <file> -` when the host has it (exact, and far cheaper than page images), else read the pages. Write every transaction line to `data/inbox/.staged/<name>.csv` with the header `date,description,amount,balance`: ISO dates, money out negative, the running balance where the statement prints one and blank where it doesn't (many banks print it once a day), and nothing else (no address, no account number, no summary rows). Decide money in or out by the column each amount sits under on its own page, since columns shift between pages; never from the change in balance, which would make the proof prove nothing. Note the printed opening and closing balances and the period; for a card, the payment due date and the amount due. When the statement prints totals (deposits and withdrawals, with counts), check your lines add up to them before importing. If a page is illegible, stop and say which, rather than guessing a line.
5. **Dry run:** `bun "${CLAUDE_SKILL_DIR}/scripts/import.ts" <file> --account <id> --dry-run`, adding `--original <pdf>` for a staged PDF, `--opening`/`--closing` when the statement prints them, `--from`/`--to` for its period, and `--due`/`--amount-due` for a card. A refusal names its reason. A balance that does not follow is a misread: re-read that page of a PDF, or fix the column map's sign or debit and credit. Never change a figure to make the check pass.
6. **Import:** the same command without `--dry-run`. The engine files the original under `data/originals/<entity>/<YYYY-MM>/`, appends the new lines to `data/transactions/`, records the statement in `data/statements.csv`, and adds the tax ledger's `statement` row once per account and month, so the books show that month's statement as in.
7. **Say what wasn't proven:** a statement with no balances printed anywhere imports as `unchecked`; tell the operator and ask for one with balances when the account matters for the books. Importing that one replaces the unchecked import of the same period (the report names it under `replaced`). One the engine reports as `alreadyImported` added nothing; delete its inbox copy only on the operator's yes. When the institution's export never carries balances (a card or wallet that lists purchases only), say so, and with the operator's yes mark the account `balances: false` in its profile: it then counts for spending only, shows as such on the Accounts page, and stays out of the "adds up" health item. Lines in several currencies go one account per currency, as in step 3; the same original can feed each of those imports (`--original` on every one), and a second import of it into the same account is still caught.

**Reply:** one line per statement (account, period, lines added and already known, checked or unchecked), where each original was filed, and anything refused with its reason and the fix.
